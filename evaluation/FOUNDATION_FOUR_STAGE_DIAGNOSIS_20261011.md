语义代理不严格、Top-K 与 SRC 选择脱节。不能据此量化每项对 F1 的因果贡献。
此次只新增诊断工具及本报告，没有修改预测源码、模型、图缓存、冻结结果或配置，
没有调用 LLM、重建 CPG、访问锁定测试集或上传 GitHub。

检查对象为 `development/type_coverage_reconstructed_20261008/src/`，47 个文件
仍与冻结基础一致，而非根目录修复版或近期窗口候选。现有完整词法审计来自

508 次首轮请求：SRC/DEP 全部逐字一致；254 份冻结 DOT 和包装源码哈希全部吻合。
因此该审计的证据存活统计适用于当前基础版的首轮输入。

复核回执：`output/foundation_four_stage_diagnosis_v2_20261011.json`。

## 1. 图构建：有明确坏图，包装语义有风险

- idx146 的冻结图有 140 节点、378 边，但 CALL=0、RETURN=0，最终没有 Top-K。
  图非空不能证明目标函数体可用。全量检查中仅该行没有 CALL；有 CALL 也不能
  证明其他行的 CFG/DFG 完全正确，不能把所有图称为已通过语义验证。
- `sven_eval/data/wrap_slice.py` 的包装只补函数外壳并添加通用类型桩，
  不恢复片段缺失的内部控制作用域、声明或 helper 契约。类型桩甚至将
  `mrb_context.stack/stbase/stend` 写为 int，不能当作真实指针类型/布局。
- `graph/build_cpg.py:63` 的门槛验证 METHOD→AST→BLOCK，不验证每个原始
  可执行语句是否进入操作节点。当前实测使用已冻结 CPG，未重新通过构建门槛。
- `graph/load_graph.py` 的 DOT 加载没有保留每节点文件归属及外部性，
  不能据此严格排除类型桩/外部声明。`graph/pipeline.py:24` 的异常 JSON
  回退也未绑定源码指纹，这是通用风险，尚无证据证明本批发生陈旧 JSON 回退。

建议：先记录目标函数体、原始语句映射、真实文件/外部节点归属和明确的失败状态。
不能删除 idx146，不能为降低失败率臆造作用域或偷偷重建冻结图。

## 2. 图压缩：保护危险词不等于保护依赖链

- `graph/summarize_graph.py:505` 按节点 code 中 API 词命中 force-keep，
  不限操作节点。包含整段代码的 BLOCK/METHOD 同样可获保护和较高分，
  重复计算危险词不能替代精确调用/读取点识别。
- 节点阈值与预算裁剪未约束“读取对象→索引/宽度→长度更新→守卫”的依赖闭包。
  保住 sink 仍可能删掉判别其安全性的长度更新，现有全量统计证明这种丢失存在。
- `graph/summarize_graph.py:590` 的连通修复按 ID 顺序只试 u→v，
  在全部边上做 shortest_path/has_path；AST 可达不能证明数据依赖已经恢复。
  最后预算裁剪还能再拆断恢复链，并在预算压力下删除部分 force-keep 节点。
- token 预算采用固定每节点 8、每边 4 的估计，并非真实完整表达式展示成本。
  压缩图在估计预算内，不意味着有用证据能塞进最终 260 字符路径。

建议：以操作节点及其必要依赖为预算单位；区分 AST 归属、数据依赖和控制依赖，
预算裁剪后重新验证证据闭包，而不是仅验证普通图可达。

## 3. 路径检索：对象绑定与排序目标不严格

- `retrieval/path_ranker.py:88` 的 lifecycle 特征只看路径内事件文字，不校验
  同一对象、别名和可执行顺序。合成复现：`free(a)`→CFG→`printf("%s", b)`
  得到生命周期分 7.0，虽然使用的是无关变量 b。source-sink 完整度也只按
  路径索引先后计分，混合 AST/REF 路径顺序不能当作程序执行顺序。
- 起点偏向 API；只有没有匹配 API 才回退真实调用，只有没有真实调用才选择
  读取/比较运算符。存在辅助调用时，关键数组读取未必成为起点。
- 只向前遍历混合边，不做读取点向定义/长度更新/控制条件的反向依赖检索。
  压缩图只要还有任意候选，就不会回原图补遗漏的关键读取证据。
- 排序以 Generic 为默认，pipeline 未传压缩阶段推断的类型；压缩与检索不是
  严格共享目标。危险词密度、容器代码、调用数量及混合边类型会影响排名。
- 多样性惩罚主要针对相同首尾节点，不能消除不同尾部却有相同展示前缀的路径。
- `candidate_paths.py:179` 有跳数边界错误：max_hop=1 实际可生成 2 条边。
  另有去重前枚举上限、孤立起点不生成单节点候选等工程限制。

建议：先纠正对象绑定语义和预算下的有效证据定义，再设计单一候选；不要按
已知 CWE 标签挑规则，也不要将 AST 路径当成已证明漏洞链。

## 4. 源码切片/展示：确定性漏语句与检索脱节

- `linearization/typed_paths.py:481` 在当前 SOURCE_SLICE_ASSIGNMENT_FIX=0
  时不匹配普通 `n = 7;` 或 `n++;`，且将 `*p = 1;` 视作注释丢掉。
  三者均在足够大预算下复现，故不是预算不足造成的遗漏。
- `_collect_graph_anchors:601` 当前收集传入图全部 code≥6 的节点。
  Top-K 再添加这些节点完全冗余，254/254 行锚点不因移除 Top-K 而变化。
  这不代表图完全没有作用，而是 SRC 选择不依赖检索选中的 Top-K。
- 当前 SRC 为启发式过滤与行评分，不是研究计划描述的严格反向程序切片。
  删除纯大括号及稀疏拼接会失去作用域；前两行强制保留也不保证签名完整。
- Top-K 配置 15，首轮实际仅展示前 2/4 条；每节点 code 截 35 字符，
  每路径再截 260/300 字符，可能截断表达式、边或尾部 sink。证据头却扫描
  整条路径，故可能声明正文看不见的危险操作。
- 最新实际首轮共展示 506 条路径；366 条结尾不是序列化节点闭合 `]`，
  可确定存在整串截断（这是下界，不涵盖所有节点内部截断）；50/254 行
  的展示字符串存在完全重复。并非 Top-K 有 15 条就给模型看了 15 条证据。

建议：优先单独修复语句保真，在固定预算内保留完整语句、原始行号与省略边界；
随后单独试对象绑定的反向依赖切片及展示预算一致性，不直接再次扩写全部源码。

## 四阶段之外的混杂与实施顺序

最新基础版 508 次真实调用中，491 次 finish_reason=length。输出截断/判定解析
是独立问题，不能把基础版低 F1 全部归因于图，也不能用离线词法覆盖预测新 F1。
近期“窗口＋对齐＋紧凑输出”联合候选质量下降，说明工程完整性不保证分类收益；
不能将其下降单独归因于窗口或紧凑输出。

推荐顺序：

1. 保留基础与全部历史结果，新增语句保真回归约束，单独候选修复普通赋值/
   自增/解引用漏行；不同时更改压缩、排序、提示和判定。
2. 独立诊断对象绑定的排序代理，验证同对象、定义—使用与控制作用域，避免
   把词法共现升级为漏洞事实。
3. 再独立比较依赖闭包压缩、反向检索和预算一致展示；每次覆盖全部254行，
   同时报源码/家族单位统计，保留失败和缺失契约。
4. 新真实 LLM 对照须另行批准；先冻结单一改动并核验全量输入，再比较效果。
   当前 SVEN 已曝光，任何结果都不替代独立论文测试。
